01

目标与设计原则

后端不是一个 CRUD 服务，而是“确定性证据编排 + AI 推理”的诊断系统。

核心目标

  • 稳定接收前端/SDK/插件产生的问题 Context。
  • 解析并标准化 Network、Console、Error、Page、WebSocket、Business Event 等不同类型数据。
  • 通过服务映射、日志系统、源码仓库补充“运行时证据”。
  • 将高质量、可验证、范围已收窄的 Evidence 交给 AI，而不是把原始数据全部塞给模型。
  • 一次 Case 允许识别多个 Finding，并按责任域创建多个 Jira。
  • 预留 Organization / Group / Application / Capability / Analytics 维度。

五条架构原则

  1. Case 是聚合根：所有现场、证据、诊断、Finding 和 Jira 都以 Case 关联。
  2. Context ≠ Evidence：Context 来自现场；Evidence 是后端主动补全得到的外部证据。
  3. Finding ≠ Case：一次 Case 可拆成多个独立前端/后端/集成问题。
  4. Deterministic first：能通过 URL、traceId、stacktrace、repo mapping 确定的事情不交给 AI 猜。
  5. AI Provider 可替换：Devin 只是 DiagnosisProvider 的一个实现。
系统主线： Group → Diagnosis Case → Context → Evidence → Diagnosis Run → Findings → Jira Tickets

Elastic / Kibana 日志查询

业务侧常说“查 Kibana”，但架构层建议抽象为 LogSearchClient；如果底层允许，优先直接查询 Elasticsearch，而不是耦合 Kibana UI 内部接口。

9.1 查询优先级

1 · traceId

最精确，优先使用

2 · transactionId

银行交易场景高价值关联键

3 · sessionId

跨前后端 Session 关联

4 · service + time

兜底：API + ±N 秒
POST /{index-pattern}/_search
{
  "size": 100,
  "query": {
    "bool": {
      "filter": [
        { "term": { "transactionId.keyword": "TX-938184" }},
        { "range": {
            "@timestamp": {
              "gte": "2026-08-30T13:20:26Z",
              "lte": "2026-08-30T13:20:36Z"
            }
        }}
      ]
    }
  },
  "sort": [{ "@timestamp": "asc" }]
}

9.2 返回后处理

  • 只保留 ERROR / WARN / exception stack / request correlation 等高价值日志。
  • 对重复日志做 fingerprint 去重。
  • 提取 class、method、file、line 等代码线索。
  • 保存“查询条件 + 查询时间 + 原始引用”，保证诊断可审计和可复现。
9.1

Context 与 Evidence 的关系模型

为了保证 AI 结论可解释，Evidence 不能只是“都属于同一个 Case”；后端需要记录 Evidence 是由哪条 Context 触发、是否由上一条 Evidence 继续派生。

图 6A · Context → Log Evidence → Source Evidence → Finding

因此建议 diagnosis_evidence 至少保留以下关系字段：

source_context_event_id  // 由哪条现场 Context 触发
parent_evidence_id       // 是否由另一条 Evidence 派生
fingerprint              // 同类证据去重
source_system            // ELASTIC / BITBUCKET / SOURCEMAP / MAPPING
10

Bitbucket / 源码定位

源码定位同样遵循“确定性优先”：先通过 Service Registry 和 Stacktrace 缩小范围，再让 AI 在候选代码内推理。

示例： /ms-name/inquiry/account-info → ms-name → account-ms repo → AccountInquiryService.java:184 → 读取 150~220 行 → AI 分析

10.1 Service Registry 推荐模型

{
  "applicationId": 42,
  "urlPatterns": ["/ms-name/**"],
  "repository": {
    "provider": "BITBUCKET",
    "project": "CBS",
    "repo": "account-ms",
    "defaultBranch": "main"
  },
  "log": {
    "provider": "ELASTIC",
    "indexPattern": "ms-name-*"
  },
  "jira": {
    "project": "ACCOUNT"
  }
}

10.2 Source Resolver 顺序

  1. 从 URL / Application 获取目标 Repository。
  2. 如果日志带 Class.java:line，直接计算文件候选。
  3. 根据 buildVersion / gitCommit 确定代码版本；不得默认 main 等于线上版本。
  4. 只取命中行附近窗口（例如 ±50 行）和必要依赖方法。
  5. 没有精确 stack 时，再做 symbol / endpoint / exception message 搜索。
  6. 形成 SOURCE_CODE Evidence，而不是直接交给 AI 远程漫游整个仓库。

AI Diagnosis Orchestrator / Devin Integration

这一层的目标不是“Java 调一次 Devin API”，而是把 Devin 纳入一个可重试、可审计、可验证、可替换的诊断工作流。Java 是 Orchestrator，Devin 是 Reasoning Provider。

业务层只依赖中立接口，不能依赖 Devin Session DTO：

    Optional<DiagnosisProviderResult> getResult(String providerSessionId);
    void cancel(String providerSessionId);
}

public record DiagnosisSubmission(
    String provider,
    String providerSessionId,
    ProviderStatus status

    └── DevinDiagnosisProvider
         ├── DevinRequestBuilder

11.2 当前 Devin API Contract（v3）

按当前官方 v3 文档，创建组织级 Session 使用：

Authorization: Bearer <token>

对本项目最有价值的请求字段包括：

Devin 字段Sherlock 用法
prompt诊断目标、边界、约束；不承载所有原始数据
repos限定当前 Case 允许 Devin 访问的 Repository

11.4 Context Builder 的裁剪规则

数据进入 AI 的规则
Network失败请求、慢请求、与错误时间窗口/trace 关联的请求优先
ConsoleERROR、关键 WARN、与失败请求相关日志
Backend Logstrace/transaction 精确匹配优先；去重后保留异常上下文
Source只传候选文件/方法/行号窗口，不默认传整个仓库文本
Raw Payload不直接发送；只作为 Case 审计原始数据
敏感字段在 DiagnosisContextBuilder 前完成 masking / removal

11.5 Prompt 设计

You are performing an evidence-based software diagnosis.

Analyze only the supplied case context, evidence and authorized repositories.

Goals:
1. Identify every independent technical finding.
2. A case may contain frontend, backend and integration findings.
3. For each finding, identify application, repository, file, method and line range
   only when supported by evidence.
4. Explain the most probable root cause.
5. Recommend the minimum technical fix.
6. Reference evidence IDs for every important conclusion.

Rules:
- Do not invent repositories, files, methods or evidence.
- Split independent defects into separate findings.
- Lower confidence when evidence is incomplete.
- Prefer verified runtime evidence over assumptions.
- Do not create Jira issues or modify code in this diagnosis session.

11.7 Devin Session 生命周期

图 7A · Diagnosis Run 与 Devin Session 生命周期

当前官方 Get Session 返回 Session 状态和 structured_output；后端将 Provider 状态映射为内部 RUNNING / COMPLETED / FAILED / SUSPENDED 等有限状态。对外部状态名不在核心领域中扩散。

11.8 Polling / Timeout / Retry

建议 Polling 采用阶梯退避，例如：

5s → 10s → 15s → 30s → 30s ...

并在 Group / Capability 或系统配置中定义：

diagnosis.max-duration
diagnosis.max-retry
diagnosis.max-acu
diagnosis.poll-backoff

对于 429、5xx、网络超时可以重试；对于认证/权限/Repo 不可访问等确定性错误，应直接失败并记录原因，避免无意义重试。

11.9 Repo Access Strategy

模式Java 后端Devin适用
Evidence-only提前读取候选代码并放入 Evidence只分析提供的代码安全限制最严格
Repository-aware传入授权 Repo scope自主探索 Repo上下文完整、效率高
Hybrid（推荐）先找候选文件/代码窗口 + Repo scope在授权 Repo 内继续验证调用关系本项目最适合

11.10 Result Validation

Devin Structured Output 不能直接写入正式 Finding。必须经过 Java Validation：

验证项验证方式失败时

12.1 Finding 去重 / 合并策略

  • 同一 Run 内按照 application + file + method + rootCause fingerprint 做基础去重。
  • 不同 Finding 责任域不同，默认不合并。

性能、索引与分区

MVP 不做复杂分库分表；优先保证主查询路径上的联合索引、批量写入和大字段控制。

18.1 核心索引

CREATE INDEX idx_case_group_created
    ON diagnosis_case(group_id, created_at DESC);

CREATE INDEX idx_context_case_time
    ON context_event(case_id, event_time, sequence_no);

CREATE INDEX idx_context_transaction
    ON context_event(transaction_id)
    WHERE transaction_id IS NOT NULL;

CREATE INDEX idx_context_trace
    ON context_event(trace_id)
    WHERE trace_id IS NOT NULL;

CREATE INDEX idx_evidence_case_type
    ON diagnosis_evidence(case_id, evidence_type);

CREATE INDEX idx_finding_case_type
    ON diagnosis_finding(case_id, finding_type);

CREATE INDEX idx_job_pending
    ON diagnosis_job(status, next_retry_at, created_at)
    WHERE status = 'PENDING';

18.2 JSONB 使用边界

字段类型存储方式
group_id、case_id、event_time、traceId、type、status、application普通列 + B-tree
复杂 request/response 摘要、原始第三方响应、扩展字段JSONB
超大附件 / 视频 / 截图对象存储或文件服务，数据库只存 reference

18.3 分区

当 Context Event 达到千万级以上并出现明显维护压力时，再对 context_event.event_time 做 PostgreSQL 月分区。Hackathon 不实施；DDL 层不要人为引入 hash 分库。

18.4 存储过程

核心业务逻辑放 Java。存储过程仅考虑归档、分区维护、retention cleanup、离线聚合；Parser、Evidence、AI 编排不进入数据库过程。

银行环境下，Context 与日志可能包含客户信息、账户信息、Token 和内部代码，安全设计必须进入后端第一版。

Request/Response 含敏感字段白名单字段采集 + Server-side Masking + 大 Body 截断

审计记录谁查询了 Case、谁触发 AI、谁创建 Jira、外部 Provider 请求 ID
