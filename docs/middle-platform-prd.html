01

中台定位与核心价值

中台不是又一个 Admin CRUD，而是 AI Sherlock 从"采集→诊断→修复→发布"全链路的中枢驾驶舱。

信息汇聚中枢

将 Chrome 插件采集的现场数据（Network、Console、Error、截图、录屏）、内部多仓源码（Bitbucket 多项目多仓库）、多种日志系统（Elastic/Kibana、业务审计日志）统一汇聚并关联绑定，消灭信息孤岛。

项目维度驱动

一切数据以"项目"为核心组织单元。每个项目绑定其前端仓库、后端微服务仓库、日志索引、JIRA Project、负责人（Owner），形成从问题发现到责任归属的完整闭环。

AI 闭环引擎

LLM 诊断结果在 JIRA 中呈现，人工审批通过后一键触发 LLM 自动修复源码并创建 PR，PR 结果回写 JIRA，Merge 后自动发布到 UAT 环境 — 全程不离开中台 & JIRA。

中台主线： 项目注册 → 仓库/日志绑定 → 插件采集入库 → Case & Finding 生成 → JIRA 看板 → LLM 分析 → 人工审批 → 自动修复 & PR → Merge → UAT 发布

3.1 页面结构

公开首页（Landing Page）

  • Hero 区域：产品 Slogan + 一句话价值主张 + 主视觉
  • 功能亮点：3-4 个核心能力卡片（一键上报、AI 诊断、自动修复、全链路追踪）

  • 数据看板（可选）：展示脱敏后的实时统计数字（今日 Case 数、平均诊断耗时、修复成功率）
  • 导航栏：右上角 [登录] 按钮，已登录用户显示 [进入控制台]
  • Footer：文档链接、版本信息、联系方式

双通道认证策略

  • 外网通道 — Google OAuth 2.0：
    • 零运维，用户无需注册/记密码，覆盖率最高
    • Google email 作为用户唯一标识，绑定内部角色
    • 可配置 email 域名白名单（如仅允许 @company.com），兼顾开放与安全
    • 对接 Google Identity Services SDK，前端 Sign In With Google 按钮
  • 内网通道 — 企业 SSO（OIDC / SAML）：
    • 对接企业 AD/LDAP 已有用户体系，登录后自动同步 Organization / Group
    • 银行/企业场景必选，满足合规与审计要求
    • 支持 SAML 2.0（ADFS / Okta）和 OIDC（Keycloak / Azure AD）
  • 辅助通道 — 用户名密码（MVP 开发用）：
    • 仅用于本地开发、演示和 Hackathon，生产环境可关闭
    • 对接后端 POST /api/v1/auth/login

3.2 统一身份模型

核心原则：一个 Email，一个用户

不管通过 Google OAuth 还是企业 SSO 登录，中台后端只认一个 User 模型。 以 email 作为主键，OAuth 和 SSO 只是两种 AuthProvider 实现。 同一用户可能同时拥有两种登录方式（如公司邮箱既是 Google Workspace 又接了 SSO），不会产生重复账号。

User 数据模型

idBIGSERIAL PK
emailVARCHAR UNIQUE — 用户唯一标识
display_name显示名称（从 Provider Profile 同步）
avatar_url头像（从 Provider Profile 同步）
auth_providerGOOGLE / SSO / PASSWORD（首次注册通道）
auth_provider_idProvider 侧唯一 ID（Google sub / SSO NameID）
organization_idFK — 所属组织（SSO 自动同步，Google 首次登录分配）
roleADMIN / PROJECT_OWNER / DEVELOPER
last_login_at最近登录时间
statusACTIVE / SUSPENDED

3.3 登录流程与时序

Google OAuth 流程

点击 Google 登录
→
Google 授权页
→
回调 /auth/google/callback
→
JWT 签发
  1. 前端渲染 Sign In With Google 按钮（Google Identity Services SDK）
  2. 用户授权后，前端获得 credential（ID Token），发送到后端
  3. 后端验证 Google ID Token 签名 + 提取 email / name / picture
  4. 域名白名单校验（可选）
  5. 按 email 查找或自动创建 User 记录（auth_provider=GOOGLE）
  6. 签发 JWT（Access Token 15min + Refresh Token 7d），写入 HttpOnly Cookie
  7. 前端按角色路由到对应页面

企业 SSO 流程

点击企业登录
→
SSO 登录页
→
SAML/OIDC 回调
→
JWT 签发 + 组织同步
  1. 前端 [企业登录] 按钮 → 重定向到 SSO IdP 登录页
  2. 用户在 IdP 完成认证（含 MFA，由 IdP 控制）
  3. IdP 回调后端 /auth/sso/callback，携带 SAML Assertion / OIDC Code
  4. 后端验证签名 → 提取 email / name / groups / department
  5. 按 email 查找或创建 User（auth_provider=SSO）
  6. 自动同步：从 SSO groups 映射到 Organization / Group / Role
  7. 签发 JWT，同 Google 流程

3.4 Session 管理 & 安全

策略说明
Access TokenJWT，15 分钟有效，携带 user_id / role / organization_id，存入 HttpOnly Cookie
Refresh Token不透明字符串，7 天有效，存入 HttpOnly Cookie，支持 Token Rotation（用一次换一个新的）
Token 刷新Access Token 过期时前端 401 → 自动调 /api/v1/auth/refresh 获取新 Access Token
登出清除 Cookie + 后端标记 Refresh Token 失效
域名白名单Google OAuth 可配置允许的 email 域名列表，非白名单域名拒绝登录
登录审计记录每次登录的 provider / IP / User-Agent / 时间，写入 audit_log
多设备允许同一用户多设备同时在线，不互踢

5.1 项目注册与配置

每个"项目"是中台的一等公民，承载以下绑定关系：

配置项说明示例必填

5.2 源码仓库绑定详情

仓库绑定流程

  1. Admin 在中台填写 Bitbucket 仓库地址（Project + Repo slug）
  2. 中台调用 Bitbucket API 验证仓库可达性（GET /rest/api/1.0/projects/{p}/repos/{r}）
  3. 获取默认分支、最近 Tag/Commit，缓存仓库元信息
  4. 配置 URL Pattern → 仓库的映射规则（支持 Ant-style 通配符）
  5. 配置 Build Version → Git Commit 的映射方式（Tag / Commit Hash / CI Build Number）
  6. 保存绑定关系，后续 Case 自动使用该映射进行源码定位

日志系统绑定流程

  1. Admin 填写 Elastic 索引 Pattern（如 account-ms-*）
  2. 中台调用 Elastic API 验证索引存在且可查询
  3. 配置日志字段映射：
    • 时间字段：@timestamp
    • 级别字段：level
    • TraceId 字段：traceId / transactionId
    • 消息字段：message
    • 异常栈字段：exception.stack_trace
  4. 配置关联的服务名称（用于 Finding 路由）
  5. 保存绑定，Evidence Resolver 自动使用
Service Registry 数据模型复用：中台的项目管理直接操作后端 service_registry 表，与后端技术设计文档 §10 的 URL→Service→Repo→JIRA 映射完全对齐。前端多仓 MFE + Qiankun 场景下，一个项目可绑定多个前端仓库，通过子应用路由前缀区分。

项目选择器

8.3 修复 Session 的 Prompt 策略

修复 Prompt 模板（核心要素）

## 修复任务

你是 AI Sherlock 自动修复引擎。请根据以下诊断结果修复代码缺陷。

### 问题定位
- **仓库：** {repository}
- **分支：** {branch} (基于 commit {commitHash})
- **文件：** {filePath}
- **方法：** {methodName}
- **行号范围：** L{lineStart} - L{lineEnd}

### Root Cause
{rootCauseSummary}

### 推荐修复方案
{recommendedFix}

### 相关证据
{evidenceSnippets}

### 约束
1. **仅修改**上述指定的文件和方法范围，不得扩大修改面
2. 保持现有代码风格（缩进、命名规范、import 顺序）
3. 修复必须是**最小化变更** — 不要重构不相关的代码
4. 如果存在相关单测，修复后确保测试通过
5. 如果发现 Root Cause 分析有误或无法修复，请在 Structured Output 中说明原因

### 输出要求（Structured Output）
{
  "status": "FIXED" | "CANNOT_FIX",
  "modifiedFiles": [{ "path": "...", "diffSummary": "..." }],
  "testResult": "PASS" | "FAIL" | "NO_TESTS",
  "explanation": "...",
  "cannotFixReason": "..." // 仅 CANNOT_FIX 时
}

8.4 审批策略与安全控制

审批规则

  • 必须人工审批：LLM 修复必须经过 Owner 或授权 Developer 点击 [批准修复] 后才执行
  • Confidence 阈值：system_confidence < 0.6 的 Finding 默认隐藏 [批准修复] 按钮，需 Owner 手动开启
  • 批量审批：Admin 可对同一项目下多个 Finding 批量审批（谨慎使用）
  • 审批记录：谁在什么时间批准，记录到 audit log

安全控制

  • 仓库白名单：LLM 修复 Session 仅可访问 Finding 关联的目标仓库
  • 分支隔离：修复在独立分支 fix/{findingKey} 上执行，不直接写 main
  • 修改范围约束：Prompt 明确限定文件/方法范围，LLM 超范围修改在 PR Review 中暴露
  • 自动回滚：若 LLM 修复 Session 超时或失败，自动清理临时分支
  • 成本上限：每个修复 Session 设置 max_acu_limit，防止 Token 失控

8.5 触发入口：命令与 Workflow

人工确认 LLM 分析正确以后，触发自动修复不能只依赖一个页面按钮，还应该同时支持 中台按钮、JIRA Workflow Transition 和 命令式触发 三种入口，这样能覆盖产品、研发和平台团队的不同工作习惯。

触发方式入口位置适用场景触发结果
页面按钮 中台 JIRA 看板、Case 详情页 Owner 在浏览中台时直接确认 调用 /api/v1/findings/{findingKey}/approve-fix
JIRA Workflow JIRA Issue 的 Transition 按钮 研发习惯在 JIRA 内完成全部推进动作 Transition 到 Fix Approved 时由 Webhook 回调中台触发修复
命令触发 中台内命令菜单、快捷操作、后续可接 IM Bot 批量操作、自动化脚本、群里快速处理 执行统一编排命令，如 approve-fix、retry-fix、deploy-uat

10.3 中台触发发布的方式

方式 A — Webhook 直通（推荐）

Bitbucket PR Merge 事件 → Bitbucket Webhook → CI/CD Pipeline 自动触发。
中台仅监听 Merge 事件更新状态，不介入 Pipeline 执行。
优点：延迟低，CI/CD 原生支持。
适用：已有成熟 CI/CD Pipeline 的项目。

方式 B — 中台 API 触发

Bitbucket PR Merge → 中台 Webhook → 中台调用 CI/CD API 触发部署。
中台作为调度中心，可在触发前做额外校验（如检查关联 Case 是否全部修复）。
优点：中台可编排多步骤发布逻辑。
适用：需要中台介入发布决策的场景。

10.4 发布结果回写

成功：CI/CD Pipeline 完成后回调中台 Webhook → 中台更新 fix_pipeline 为 UAT_DEPLOYED → JIRA Transition → Done → 中台看板显示 ✅。

失败：CI/CD 回调失败信息 → 中台更新为 DEPLOY_FAILED → JIRA Add Comment（含失败日志摘要）→ 通知 Owner 处理。

10.5 自动发布前置条件

前置条件校验方式不满足时处理
PR 已 Merge Webhook 或轮询获取代码平台最终状态 未 Merge 不触发 UAT
项目开启自动 UAT 检查 project.capability_profile 与发布配置 若关闭，则只回写"可手动发布"
CI/CD Pipeline 配置有效 项目配置校验 + 最近一次连通性检查 回写 JIRA Comment，提醒 Owner 补配置
必要质量门禁通过 至少满足编译成功、基础测试通过、镜像构建成功 进入 DEPLOY_FAILED 并中止后续动作

15

风险与应对

中台系统的核心风险识别与缓解策略。

#风险影响概率缓解策略
1 LLM 修复质量不稳定 PR 被拒绝率高，Developer 信任度下降 中 • Confidence 阈值控制（低置信度不显示批准按钮）
• 修复 Prompt 持续优化，记录每次修复的成功/失败
• 提供 [重试修复] 能力，允许 Developer 补充上下文后重试
2 JIRA API 限流 / 不可用 工单同步延迟，状态不一致 中 • 异步 Job Queue + 重试策略（复用后端 PostgreSQL Job Queue）
• 本地缓存 JIRA 状态，Webhook 优先，轮询兜底
• JIRA 不可用时中台仍可查看历史数据
3 Bitbucket Webhook 配置复杂 PR 状态无法实时同步 中 • 提供 Webhook + 轮询双模式
• 项目管理页提供 Webhook 配置向导（自动生成 Webhook URL + Secret）
• 轮询模式每 5 分钟一次作为 fallback
4 LLM 修复引入新 Bug UAT 环境不稳定 高 • PR 必须经过人工 Review 后才能 Merge（中台不自动 Merge）
• UAT 部署后自动运行冒烟测试
• 部署失败自动回滚
• 修复 Session 限定最小修改范围，降低副作用面
5 项目配置不完整导致 Case 路由失败 新 Case 无法匹配到项目，Evidence 补全缺失 中 • 项目创建时强制验证（仓库可达、日志可查、JIRA 可连）
• 未匹配项目的 Case 进入 Unassigned 队列，Admin 可手动分配
• 配置健康度检查 Dashboard
6 UAT 自动发布影响现有流程 团队不接受自动部署到 UAT 中 • MVP 仅支持 Webhook 直通方式（复用已有 CI/CD）
• 提供开关：项目级可关闭自动 UAT 部署
• 首次使用建议先在少数试点项目验证
核心约束：中台不自动 Merge PR。
LLM 创建的 PR 必须经过人工 Review + Approve 后才能 Merge。中台仅负责创建 PR、设置 Reviewer、同步状态。Merge 操作由 Developer / Owner 在 Bitbucket 中完成（或通过 Bitbucket 的 Auto-Merge 功能在满足条件后自动 Merge）。这是安全底线。

附录：端到端场景演示

以一个真实的 Bug 场景走完全流程，展示中台在每个环节的呈现。

场景：账户查询接口 NPE

  1. QA 上报：QA 在 Chrome 插件中截图 + 描述"点击查询按钮后页面无响应"，提交
  2. 后端接收：POST /api/v1/cases → Case SH-20260902-X7K12 创建
  3. Evidence 补全：
    • Network 捕获 GET /api/account/info → 500
    • traceId=abc-123 → Elastic 查到 NPE 日志
    • account-ms 仓库 → AccountService.java:184 截取源码
  4. LLM 诊断：Devin 分析 → Finding: null-handling bug in AccountService.queryAccountInfo()
  5. JIRA 创建：ACCOUNT-850 自动创建，Assignee = 张三（项目 Owner）

续：修复 & 发布

  1. 中台展示：JIRA 看板 ACCOUNT-850 行显示"已分析 92%"
  2. 人工审批：张三在中台点击 [批准修复]
  3. LLM 修复：Devin 在 fix/finding-FND-401 分支添加 null check
  4. PR 创建：PR #128 → account-ms，Reviewer = 张三
  5. JIRA 同步：ACCOUNT-850 自动添加 PR 链接 Comment
  6. 人工 Review：张三在 Bitbucket Approve PR
  7. Merge：张三 Merge PR → main
  8. UAT 部署：Bitbucket Webhook → Jenkins → account-ms-uat 部署成功
  9. JIRA Done：ACCOUNT-850 自动 Transition → Done
  10. 中台看板：修复状态列显示 ✅ UAT 已发布
全程耗时估算：上报 → AI 分析（~2 min）→ 人工审批（~5 min）→ LLM 修复（~3 min）→ PR Review（~10 min）→ Merge → UAT 部署（~5 min）。从问题发现到 UAT 验证约 25 分钟，传统流程通常需要 1-3 天。
